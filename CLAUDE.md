# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Cábala (cabala.ar) — predict Argentine football (Liga Profesional, Copa Libertadores, Copa Sudamericana) match outcomes, earn points based on odds, and compete on a leaderboard. Next.js 16 (App Router) + React 19, Postgres via Drizzle ORM, Better Auth, TanStack Query. UI text/copy is in Spanish (Argentina).

## Commands

- `pnpm dev` — start the dev server
- `pnpm build` — production build
- `pnpm lint` — ESLint (flat config, `eslint-config-next`)
- No test suite exists in this repo.

Database (Drizzle + Postgres, config in `drizzle.config.ts`, schema in `db/schema.ts`). No `drizzle/` migrations directory exists — schema changes have never been captured as tracked migrations, so `push` is the working convention, not `generate`/`migrate`:
- `pnpm drizzle-kit push` — push schema directly (⚠️ as of this writing, `push` crashes with `Cannot read properties of undefined (reading 'replace')` while introspecting this project's live Supabase DB — likely tripped up by some existing constraint drizzle-kit's introspector doesn't handle. If it recurs, the fallback is writing the equivalent `CREATE TABLE`/`CREATE INDEX` SQL by hand against `DATABASE_URL` and keeping `db/schema.ts` as the source of truth manually.)
- `pnpm drizzle-kit studio` — browse the DB
- `drizzle-kit` reads `DATABASE_URL` from `process.env` only — it does **not** load `.env.local` itself, so prefix commands with it, e.g. `DATABASE_URL=$(grep '^DATABASE_URL=' .env.local | cut -d= -f2- | tr -d '"') pnpm exec drizzle-kit push`.
- `DATABASE_URL` points at Supabase's transaction-mode pooler (port 6543), so `db/index.ts` passes `{ prepare: false }` to the `postgres` client — required for `db.transaction(...)` to work under that pooler (prepared statements don't survive across pooled connections otherwise). Don't drop this when touching `db/index.ts`.

One-off/data scripts (`tsx` is a devDependency; run with `pnpm exec tsx <path>`, not wired into `package.json`). Like `drizzle-kit`, these read `process.env.DATABASE_URL` directly (via `db/index.ts`) and do not load `.env.local` automatically — prefix with `DATABASE_URL=...` as above. They also don't close the Postgres connection on completion, so the process hangs after finishing its work — run them with a timeout/background and check output rather than waiting for exit:
- `scripts/seed-teams.ts` — seeds `team` rows from TheSportsDB's Argentinian Primera División team list
- `scripts/seed-career-clubs.ts` — seeds `career_club` rows for career mode (see below)
- `scripts/sync-matches.ts` — calls `syncMatches()` from `lib/sync.ts` directly (for local testing of the cron job)
- `scripts/sync-results.ts` — calls `syncResults()` from `lib/sync.ts` directly

## Architecture

### Data flow: external API → Postgres → Server Actions → React Query

All football data (fixtures, results, league table) comes from **TheSportsDB** (`lib/sportsdb.ts`, three competitions: Liga Profesina = `4406`, Libertadores = `4501`, Sudamericana = `4724`). Nothing is fetched from the client — two Vercel Cron endpoints pull from TheSportsDB and write to Postgres:

- `GET /api/cron/sync-matches` → `syncMatches()` (`lib/sync.ts`) — pulls upcoming fixtures for all three competitions, ensures the two teams exist locally (lazily inserting via `ensureTeamExists`, which calls TheSportsDB's `lookupteam.php` on demand), computes odds via `lib/odds.ts`, and inserts new `match` rows (slug generated from team names + date, `onConflictDoNothing` keyed on `apiId`).
- `GET /api/cron/sync-results` → `syncResults()` — pulls past events, matches them to `scheduled` rows in the DB by `apiId`, flips them to `finished` with scores/winner, then grades every `prediction` tied to that match: updates `isCorrect`/`pointsWon` and rolls the result into the user's `userStats` (points, correct/wrong counts, streak — streak resets to 0 on a miss).

Both cron routes are protected by a shared secret: `Authorization: Bearer ${CRON_SECRET}`, checked manually in each route handler (not via Next middleware).

**Odds/points model** (`lib/odds.ts`): a team's "strength" blends league-table position (60%) and recent form — last 5 games, `wins*3 + draws` (40%). Odds are derived from win probability (`1/probability * 100`, clamped `[110, 1500]`), so `homeOdds`/`drawOdds`/`awayOdds` on `match` are integers representing odds *100 (e.g. `120` = 1.20). Points won on a correct prediction are `round(basePoints * odds / 100)` with `basePoints = 100`.

Server Actions in `actions/*.ts` (all `"use server"`) are the only read/write path for the UI — no API routes for app data, only the two cron routes and the Better Auth catch-all (`app/api/auth/[...all]/route.ts`). Client components consume actions through TanStack Query hooks in `hooks/` (e.g. `use-matches.ts` wraps `getScheduledMatches`/`getFinishedMatches`, `use-predictions.ts` wraps `createPrediction` and invalidates the `["matches"]` query key on success).

### Auth

Better Auth (`lib/auth.ts`) with Drizzle adapter, three social providers (Google, Twitch, Kick) — each `mapProfileToUser` derives `username`/`displayUsername` from the email local-part. `username` and `admin` plugins are enabled. A `databaseHooks.user.create.after` hook auto-inserts a `userStats` row for every new user. Server-side session access goes through `lib/session.ts`: `getSession()` (nullable) and `requireUser()` (redirects to `/` if unauthenticated) — always call these instead of hitting `auth.api` directly in actions/pages. Client-side auth uses `lib/auth-client.ts` (`authClient`, mirroring the same plugins).

### Schema shape (`db/schema.ts`)

- Auth tables (`user`, `session`, `account`, `verification`) follow Better Auth's expected shape — don't rename/restructure these casually, since the adapter depends on the field names.
- `userStats` is 1:1 with `user` (PK = `userId`), tracking `points`, `correctPredictions`, `wrongPredictions`, `streak`.
- `team.id` and `team.apiId` are both set to TheSportsDB's numeric team ID (kept in sync intentionally, not surrogate keys).
- `match` stores odds as integers (see above), `competition` as a plain string enum (`"liga" | "libertadores" | "sudamericana"`), and a unique `slug` for the `/matches/[slug]` route.
- `prediction` has a unique `(userId, matchId)` constraint — one prediction per user per match — and also doubles as a social post (`content`, `likesCount`, `commentsCount`, plus `predictionLike`/`predictionComment` tables).
- `matchComment` is a separate comment thread scoped to the match itself (distinct from comments on a prediction).

### Career mode (`lib/career.ts`, `actions/career.ts`, `hooks/use-career.ts`, `hooks/use-local-career.ts`, `components/career/`)

A self-contained, fully simulated football-career game bolted onto the app — **not** wired to `lib/sync.ts`/TheSportsDB in any way; it has its own club reference data (`career_club`, 75 real clubs seeded via `scripts/seed-career-clubs.ts`, 5 per tier per nationality) and its own match simulation, entirely independent of the real Liga Profesional data pipeline. `lib/career.ts` is pure simulation math (starter probability, match rating, OVR delta, goals/assists, red cards, energy/morale, club result) with no DB/session imports, mirroring how `lib/odds.ts` stays separate from `lib/sync.ts`.

Career pacing: `SEASON_LENGTH = 2` matches per season, `age` advances by `AGE_STEP = 2` on every season rollover starting from `STARTING_AGE = 17`, and the career force-retires the moment the next step would reach `RETIREMENT_AGE = 32` (clamped to exactly 32, even though the raw 17+2n sequence would otherwise land on 33). OVR is derived from 5 attributes (`computeOvr`), never stored independently, and growth is deliberately biased upward (not equilibrium-centered): `RATING_GROWTH_TIERS` only ever subtracts below a 4.0 rating, and goals/assists add a further `GOAL_OVR_BONUS = 3` to shooting / `2` to passing on top of the rating-based delta. Tuned by simulating full careers: a 16-match career lands around 84-88 final OVR (spread ~74-93), so the ceiling stays reachable but not automatic. Retune with a throwaway script whenever the energy economy changes — energy feeds `computeRating`, so growth and energy can't be tuned independently (fixing the energy flatline alone pushed average final OVR from 85 to 96). `getStarterProbability()` returns exactly 1 above a per-tier `AUTO_STARTER_OVR` bar (62/55/`MIN_OVR`) — benching is a punishment for a genuinely bad player, not the default experience, and sits under 1% of matches for a career starting at `STARTING_OVR = 60`. Club tier drives offers and simulation but is **never surfaced in the UI** — the player picks clubs by name/crest only. On every non-retiring season rollover, `pickTransferOffers()` generates 3 OVR-weighted random clubs from *any* nationality (excluding the current club) as `pendingOffers` on the `LocalCareer`, which replaces the "Simular próximo partido" button in the dashboard until the player picks one or stays. All 75 `career_club` rows are **real clubs** (5 nationalities × 3 tiers × 5 clubs — real Argentine clubs plus real clubs from Brasil/España/Inglaterra/Italia), seeded via `scripts/seed-career-clubs.ts` which fetches real badge URLs from TheSportsDB's `searchteams.php` (same API `lib/sportsdb.ts` already uses) — throttled with a 600ms delay + retry-on-429 backoff, since a full 75-club run reliably gets rate-limited otherwise. `components/career/club-crest.tsx` renders that real `logo` via `next/image`, falling back to a deterministic monogram badge only if a future name lookup ever fails to match. `components/career/country-flag.tsx` renders nationality flags from `flagcdn.com` (whitelisted in `next.config.ts`); `components/career/jersey-preview.tsx` is a pixel-art SVG jersey (squad number + jersey name + club crest) shown live during creation and on the dashboard. The player identity is a single `jerseyName` (≤12 chars, uppercased) + `squadNumber` — there's no separate first/last name.

**Life-sim layer**: `career_player.energy` (0-100, drains ~8-16 per started match, recovers when benched/suspended, plus `SEASON_ENERGY_RECOVERY = 20` at every season rollover — deliberately just under one season's drain so energy trends down across a career instead of flatlining at 0, which is what happened once `getStarterProbability` started returning 1 and benching stopped being a recovery path. Below `LOW_ENERGY_THRESHOLD = 25` the simulate button becomes "Descansar" — `restMatch()` in `hooks/use-local-career.ts` burns the match as a sit-out for `REST_ENERGY_RECOVERY = 45` at the cost of morale and team reputation — and life-event options the player can't afford the energy for are disabled) and `.morale` (0-100, moves with match results/goals/red cards) both feed back into `computeRating()` in `lib/career.ts` — low energy or morale measurably hurts performance, they're not decorative. `career_player.relationshipStatus` (`"soltero" | "en pareja"`) is driven by `LIFE_EVENTS` in `lib/career.ts` (`pickLifeEvent()`) — a pool of 2-choice trade-off events (e.g. "conociste a alguien", "pelea con tu pareja") that fire at a season rollover, mutually exclusive with `pendingOffers` (never both — a coin flip decides which one shows), resolved via `resolveLifeEvent("A" | "B")` in `hooks/use-local-career.ts`. Red cards (`RED_CARD_PROBABILITY`, position-weighted, defenders foul most) zero out that match's goals/assists, apply a flat OVR penalty, and set `career_player.suspended` — the *next* `simulateNextMatch()` call auto-detects this and forces a "served suspension" sit-out (no starter roll) instead of a normal simulation. `lib/sfx.ts` is a small Web Audio oscillator synth (no external audio files) for goal/assist/red-card/whistle/level-up/click/save/miss sounds; `components/career/match-event-overlay.tsx` is a full-screen cutscene queue that plays a sound + a `motion`-animated pop-in scene for each goal/assist/red-card in a match result before the player sees the plain summary panel underneath.

**Reputation**: `career_player.teamReputation`/`.fanReputation` (0-100, both start at 50) track standing with the manager/dressing room and with fans, distinct from the energy/morale fitness stats. Match results move both automatically inside `simulateMatch()` (good ratings/wins/goals raise them, red cards tank them); `teamReputation` in turn nudges `getStarterProbability()` (a manager who trusts you plays you more) and `fanReputation` nudges `pickTransferOffers()` toward bigger clubs. Two `LIFE_EVENTS` entries (`teammate-needs-help`, `fan-request`) trade energy/morale for reputation instead of purely energy/morale, using the same optional `teamReputationDelta`/`fanReputationDelta` fields on `LifeEventOption`.

**Penalty kicks**: an occasional, fully interactive mid-match event — `rollPenaltyChance()` in `lib/career.ts` (position-weighted, goalkeepers never get one) fires only when the player started and avoided a red card. Because it needs real user input, it can't resolve inside the synchronous `simulateMatch()` call: `hooks/use-local-career.ts`'s `simulateNextMatch()` instead stashes the in-progress sim result + a pre-rolled, hidden `generateKeeperDive()` state onto `LocalCareer.pendingPenalty` and returns a `{ type: "penalty" }` result instead of a finished match. `components/career/penalty-kick.tsx` renders the goal/goalkeeper/ball as absolutely-positioned `motion.div`s over a fixed-size coordinate frame, captures a tap as a normalized `(x, y)` aim point, and calls the pure `resolvePenaltyKick()` to decide goal/save/wide (aiming near the frame edge risks going wide; aiming inside the keeper's hidden dive radius usually gets saved). `resolvePenaltyOutcome()` then folds that outcome back into the stashed sim (adjusting goals/OVR/fan reputation) and finalizes the match through the same `finalizeMatch()` helper the non-penalty path uses, so season-rollover/transfer-offer/life-event logic only lives in one place.

**Play requires no session — saving/ranking does.** Gameplay runs entirely client-side: `hooks/use-local-career.ts` holds the authoritative `LocalCareer` state in React state + `localStorage` (key `"cabala:career"`) and calls `simulateMatch()` from `lib/career.ts` directly in the browser, so anonymous users can create a character and simulate matches with zero server round-trips. `actions/career.ts` only has three jobs: serve reference data (`getCareerClubs`, no auth), let a logged-in user snapshot their current local state into `career_player`/`career_match` via `saveCareer` (auth required, `onConflictDoUpdate` upsert + delete-and-reinsert of match history, wrapped in `db.transaction(...)` — this is the codebase's first use of a DB transaction), and serve the cross-user `getCareerLeaderboard` (ranked by `ovr`, no auth to view). `saveCareer` does light server-side sanity clamping (OVR range, non-negative stats) since the state it receives is client-simulated and therefore not fully trusted — it is not full anti-cheat. `components/career/career-view.tsx` hydrates local state from a previously-saved server career on load (if `localStorage` is empty but a session + saved career exist), so switching devices doesn't orphan a saved career — and holds a loader (not the creation wizard) until that query settles, since rendering the wizard in the gap made a saved career look lost and starting a new one there would overwrite it. For a logged-in user `components/career/career-dashboard.tsx` auto-saves **once per career, at retirement** — `saveCareer` upserts the player row *and* delete-and-reinserts the whole match history, so saving on every state change was a wasteful write per match. Mid-career progress lives in `localStorage` only; the manual "Guardar carrera" button forces an earlier server copy. Guarded by a signature of the save payload (deliberately excluding `linkedToServer`, which `markSaved()` flips right after a save and would otherwise loop) plus a `failedSignature` ref so a rejected payload isn't retried until it changes.

### Routing

App Router pages under `app/`: `/` (home), `/matches`, `/matches/[slug]`, `/leaderboard`, `/profile/[username]`, `/search`, `/settings`. SEO is handled per-page (`app/sitemap.ts`, `app/robots.ts`, `app/opengraph-image.tsx`, `components/match-jsonld.tsx` for structured data) — `metadataBase` is hardcoded to `https://cabala.ar` in `app/layout.tsx`.

### UI

Base shadcn/ui components live in `components/ui/` (style: `radix-nova`, base color `neutral`, icon library `lucide`, see `components.json`). Non-UI shared components sit flat in `components/` (e.g. `match-card.tsx`, `match-detail.tsx`, `leaderboard.tsx`), with feature subfolders for `auth/`, `user/`, and `career/`. Path alias `@/*` maps to the repo root (see `tsconfig.json`).

**"Ticket & Terrace" visual system.** The app previously went through a retro/8-bit pass (`8bitcn-ui`) that was fully reverted after user feedback that it read as generic/"AI slop" arcade styling. All `components/ui/8bit/*` files, the `retro.css` import, and the 8bit-only dependencies (`@radix-ui/react-avatar`, `-checkbox`, `-dropdown-menu`, `-label` — the base components use the unified `radix-ui` package instead) have been deleted. Every UI file now imports from the base `@/components/ui/*` only. The current system, sourced from the `anthropics/skills@frontend-design` skill, is a minimalist/premium match-day identity called "Ticket & Terrace":

- **Palette** (`app/globals.css` `:root`/`.dark`): navy `#12141c` background, cream `#f6f1e6`/`#ffffff` card, matchday gold `#b8891a`/`#c9a227` primary, desaturated celeste `#5e87a8`/`#7fa8c9` secondary, brick red `#9c3b2e`/`#c24a38` destructive. Always use the semantic tokens (`bg-primary`, `text-secondary`, etc.), never the raw hex.
- **Typography**: `Bricolage Grotesque` (`--font-heading`, applied via a `font-heading` class or the blanket `h1,h2,h3` rule) for headings, `Inter` (`--font-sans`) for body copy, `Space Mono` (`--font-mono`) for stat numbers/scores — set up in `app/layout.tsx` and `app/globals.css`.
- **Signature motion**: the `motion` package (`motion/react`, `v12`) wrapped in `MotionConfig reducedMotion="user"` in `components/providers.tsx`. `components/motion/stagger-fade.tsx` (`StaggerFade`/`StaggerFadeItem`) staggers list reveals app-wide (match lists, predictions, leaderboard rows). The one deliberate "hero" animation is the ticket-stub "¡VA CÁBALA!" stamp confirm in `components/match-card.tsx` — everything else stays calm (no scroll-triggered effects, no gratuitous transitions).
- **Ticket-stub motif**: match cards/detail (`components/match-card.tsx`, `components/match-detail.tsx`) render as a ticket stub — a `.ticket-perforation` CSS class (radial-gradient "punch" pattern, defined in `app/globals.css`) simulates a perforated tear-off edge above the date/link footer.
- **Career mode** reuses the same tokens/motion primitives: `components/career/jersey-preview.tsx` is a smooth rounded-path SVG jersey (not pixel art), `components/career/match-event-overlay.tsx` uses a `motion.div` spring pop-in instead of retro CSS `animate-bounce`, `components/career/career-ranking.tsx` and `components/leaderboard.tsx` are both hand-rolled (podium + `StaggerFade` rest-list) since the old `@8bitcn/leaderboard` block is gone — they intentionally share the same visual pattern rather than a shared component, so extend both if the ranking layout changes.
- The toast system (`sonner`) is untouched by any of this — it was never part of either UI pass.
